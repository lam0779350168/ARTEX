# Implementation Plan: ARTEX Tool & Skill Expansion

> **Scope revision (2026-11-26)**: the operator decided to keep ARTEX core (guard, intercept, target gate) unchanged. Only skill-level restrictions were removed. Guard-related items below are superseded and were not implemented.
**Branch**: `001-artex-tool-skill-expansion` | **Date**: 2026-11-26 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-artex-tool-skill-expansion/spec.md`

## Summary

Add a declarative catalog of every security-tool repo and one generic stdio JSON-RPC server binary that is launched once per repo. The server exposes `initialize`, `tools/list`, `tools/call` and `ping`, executes the declared binary with caller arguments, and returns `{target, status, findings[], raw_ref}`. Seed the existing tool registry from the catalog with capability, risk, timeout and health metadata so planners can query by capability. Rebuild every shipped skill with capability-only frontmatter, preserving operator-authored content as references. Remove active guard and scope enforcement from shipped entry points, adding no approval or sandbox mechanism.

## Technical Context

**Language/Version**: Go 1.26.11 (matches `go.mod`)

**Primary Dependencies**: Standard library only for the new server (`encoding/json`, `os/exec`, `bufio`); existing `pgx/v5` for DB migration/seed; no new module dependency

**Storage**: Existing PostgreSQL `tools` table, extended with metadata columns; raw tool output under `data/toolraw/`; catalog in `tools/catalog.json`

**Testing**: `go test` (`tools/`, `server/`, `agent/`), plus newline-delimited JSON smoke test of the server

**Target Platform**: Linux server (existing Docker image); Windows/macOS binaries built by `build.sh` as today

**Project Type**: Go service + CLI inside an existing multi-package repository

**Performance Goals**: `ping` under 5 seconds; capability queries return from in-memory registry state; heavy scan timeout >= 300 seconds

**Constraints**: No new third-party dependency; no approval/sandbox/quota code; operator's untracked files preserved

**Scale/Scope**: ~60 catalogued repos, ~15 shipped skills, one server process per repo

**Structure Decision**: Extend the existing Go module and directory layout. New code lives in `cmd/toolserver` and `tools/`; the catalog and migration are data, not new services. Skill changes stay in the existing `skills/` tree.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Guard/scope removal is enforcement-off + package removal, not full deletion of `intercept/`/`egress/` | Target-gate references span 56 Go files including dialers and their tests; full deletion is a 56-file rewrite | Rewriting core networking and deleting a large test suite has high regression risk and is harder for the operator to revert; disabling at entry points leaves no active check while keeping the build green |
| New stdio JSON-RPC loop instead of an MCP SDK | Only three methods are needed and `go.mod` has no MCP server dependency | Adding a framework dependency for three methods conflicts with the no-new-dependency constraint |
